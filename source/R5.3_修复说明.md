# AutoMesh R5.3 — 已打开 Workbench 的脚本服务自动连接

## 目标和改动

- 现有 Workbench 已启动服务时：优先按上次端口尝试连接，再扫描范围 10000–11200；还会检查当前 Workbench 进程拥有的监听端口（允许端口不在上述范围）。
- 服务尚未启动时：程序化识别 **唯一** 已运行的 Workbench GUI，再通过 Windows UI Automation 找到其 **命令窗口**；如果菜单可识别，会尝试按官方 File > Scripting > Open Command Window 打开。只在找到唯一且空的命令输入框时发送 `StartServer()`，不使用截图匹配和坐标点击。
- 执行后：从 `netstat -ano -p tcp` 比对新增监听端口；**真实验证** PyWorkbench 的系统列表和 Mesh 单元后，才把 AutoMesh 状态设为“已连接”。
- 端口框可留空、输入「自动」，或者给出端口提示；不必记住旧端口。
- 目标窗口不唯一、控件接口不支持、安全焦点验证失败、用户输入未清空时：拒绝执行，输出具体诊断；不猜测目标也不自动重发。
- 仍然**只连接现有工程**：绝不调用 `launch_workbench()`，不启动第二个 ANSYS，不会修改现有网格或进入 Fluent。
- 保留 R5.2 的警告单元二次细化预览/审核发布源文件及既有 Worker，未对其作额外重构。

## 核心技术

`AutoMesh.exe` (Go) → 使用当前已有 Python 运行时执行 `wb_server_bootstrap.py` → 通过系统自带 Windows PowerShell/.NET UI Automation 定位现有 `RunWB2`/`AnsysWBU`/`AnsysFW` 等 Workbench 窗口 → `StartServer()` → 读取本机端口变化 → `wb_cli.py` + `ansys.workbench.core.connect_workbench()` 对端口验证。

**为什么没有直接用 PyWorkbench 启动？** 官方 `connect_workbench()` 仅连接已有脚本服务器，`launch_workbench()` 会创建新的 Workbench 进程，不符合“复用当前会话”的限制。

## 测试范围及限制

- Go 原有单元测试通过；Python 169 项测试通过；Windows x64 GUI EXE 交叉编译通过。
- 在当前 Linux 工具环境**无法进行 Windows UI Automation / ANSYS 2024 R2 实机测试**，因此不能保证当前版本的 Workbench 可访问性层能暴露唯一命令输入框；若无法识别将安全停止，需读取具体日志而不是假称自动成功。
- 不通过 UI 坐标点击或图像定位操控 Workbench；不在自动失败后盲目重试，也不会自动新建 Workbench。
- 以前 R5.1 的 75 秒任务启动确认超时及其他后台队列问题，本版**没有声称解决**。本版修复范围是 **StartServer 自动启动/识别连接**。

## 验证方法

1. 保存当前工程，保留你本来打开的 Workbench 和 Meshing，关闭旧 AutoMesh。
2. 解压新包后运行 `AutoMesh.exe`，点击「连接工程」，端口字段可留空。
3. 检查状态：已有服务应直接连接；尚未开启服务时会尝试当前窗口 UI Automation 启动并自动识别端口。
4. 若出现“控件接口不可用 / 命令窗口不唯一”提示，请保留提示和 `Data/last_workbench_error.log` 供后续定位；不要反复提交命令。
